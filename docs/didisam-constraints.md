# 디디쌤 코드블럭 기술 제약사항

실제로 부딪혀서 확인한 것들만 기록. (2026-07 기준, 디디쌤 스튜디오)

## 1. 미리보기(임시저장→미리보기) ≠ 발행된 사이트

**가장 중요한 원칙**: 미리보기 화면과 실제 발행 사이트는 동작이 다르다.
- `<a>` 태그: 미리보기에서는 클릭해도 반응 없음(속성 문자열이 텍스트로 깨져 보이기도 함) /
  발행 사이트에서는 정상 작동
- `<script>` 태그, `onclick` 인라인: 미리보기에서는 전혀 실행 안 됨 / 발행 사이트에서는 정상 실행

**따라서 모든 기능 테스트는 반드시 "발행 → 실제 URL 접속"으로 해야 한다.**
미리보기에서 안 된다고 코드가 잘못된 게 아닐 수 있다. 반대로 미리보기에서 되는 것처럼 보여도
발행 후 확인 전엔 안심하지 말 것.

## 2. `<script>` 실행 여부 자체는 정상 (초기엔 차단된 걸로 오판했었음)

발행된 사이트에서 아래 전부 정상 동작 확인됨:
- 인라인 `<script>` 블록
- `onclick` 등 인라인 이벤트 핸들러
- 외부 CDN 스크립트 로딩 — 단, **cdnjs.cloudflare.com은 됨, cdn.jsdelivr.net은 응답 없이 무한 대기(차단 추정)**
- Canvas 2D, fetch(), localStorage, WebAssembly 자체 지원 — 전부 정상

**결론: cdnjs 계열 라이브러리는 쓸 수 있지만 jsdelivr 계열(Pyodide 등 다수 WASM 런타임 포함)은 피할 것.**
필요한 라이브러리가 jsdelivr에만 있다면 코드에 통째로 인라인(복사)하는 방법을 고려.

## 3. CSS/JS는 코드블럭 밖으로 그대로 샌다 — 반드시 스코프 격리할 것

코드블럭은 iframe이나 shadow DOM으로 격리되지 않고, **페이지의 실제 DOM에 직접 삽입**된다.
즉 `body { overflow:hidden }` 같은 CSS를 쓰면 사이트 전체가 그 스타일을 뒤집어쓴다.

**실제로 발생한 사고**: 게임 코드에 `body { overflow:hidden; touch-action:none; }`를
아무 생각 없이 넣었다가, 발행 사이트 전체가 스크롤이 안 되는 상태로 멈춰버림. 사용자가
"홈페이지가 안움직여져"라고 보고할 때까지 몰랐음.

**규칙**:
- `body`, `*`, `h1`, `header`, `footer` 같은 **bare 엘리먼트 셀렉터를 절대 쓰지 말 것**
- 모든 CSS는 고유 wrapper id(`#snc-root` 등) 안에 스코프 — `#snc-root .btn{}` 형태로
- 함수/변수명은 흔한 이름(`start`, `show`, `render` 등) 피하고 프로젝트 접두사 사용
  (다른 코드블럭이나 디디쌤 자체 스크립트와 이름이 겹치면 예측 불가능하게 깨짐)
- 여러 코드블럭을 한 페이지에 같이 쓸 경우 **id 충돌도 주의** — getElementById는 항상
  DOM에서 가장 먼저 나오는 요소를 반환하므로, 옛날 코드블럭을 안 지우고 새 걸 추가하면
  새 스크립트가 옛날 요소를 조작하는 사고가 남 (실제로 발생: 화면 두 개가 겹쳐 보임)

## 4. 코드 길이 제한 (정확한 숫자는 미확인, 경험적 안전선)

약 5만자(50KB) 짜리 단일 파일을 넣었더니 HTML/CSS는 끝까지 반영됐지만
**파일 끝부분의 `<script>` 내용이 잘려서 버튼이 하나도 안 눌리는 사고 발생.**
(HTML이 스크립트보다 먼저 오는 구조라 앞부분만 살아남음)

**대응**:
- 파일 하나를 **3만자(30KB) 근처로** 유지
- 넘을 것 같으면 미리 여러 코드블럭으로 쪼개서 설계
- 블록 간 통신은 하나의 블록에서 `window.함수명 = 함수` 로 전역 노출하고,
  다른 블록(반드시 페이지 순서상 뒤에 위치)에서 `window.함수명(...)` 으로 호출
- 새로 큰 코드를 넣은 뒤엔 **페이지 맨 아래 요소(예: footer 텍스트)가 보이는지** 확인해서
  최소한 HTML이 안 잘렸는지부터 체크. (스크립트가 잘렸는지는 버튼 클릭으로 확인)

## 5. 화면에 표시하는 숫자는 항상 실제 데이터와 동기화할 것

"NCS 능력단위 16개", "해양기관 88곳" 같은 칩(chip) 라벨은 하드코딩 텍스트가 아니라
실제 배열 길이 기준으로 검증해야 한다. 과거 데이터를 축소하면서 라벨 숫자를 안 고쳐서
"16개"라고 써놓고 실제로는 6개만 들어있던 사고가 있었음 — 정확한 데이터가 핵심 셀링포인트인
프로젝트에서는 이게 제일 위험한 종류의 버그다.

## 6. 디버깅 방법론

- 문제를 한 번에 여러 개 테스트하고 싶으면, 각 항목에 번호를 매기고 성공/실패를 코드 자체가
  화면에 텍스트로 찍게 만들어서 스크린샷 한 장으로 결과를 받는 방식이 효율적
  (여러 번 코드 넣었다 뺐다 할 필요 없음)
- `data:text/html;charset=utf-8,<인코딩된 HTML>` 형태의 iframe src는 외부 호스팅 없이도
  "iframe 내부에서 JS가 도는지"를 즉석에서 테스트할 수 있는 유용한 트릭
